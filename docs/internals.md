# Engine internals

How the engine works inside, for people changing it. Using the engine is documented in `Wongi.Engine` and `Wongi.Engine.DSL`. This page assumes a rough idea of how a Rete network works: an alpha side that matches facts against patterns, and a beta side that joins the matches into partial matches of whole rules.

## The network

Everything lives in one immutable `Wongi.Engine.Rete` struct, and every operation returns a new one.

- **Working memory.** `wmes` is the set of facts. `indexes` index them by every combination of one or two fields, which is what `Rete.select/2` uses to find the facts matching a template.
- **Beta network.** `beta_table` maps node refs to nodes, and `beta_subscriptions` maps a node to its children. `alpha_subscriptions` maps a template, with `:_` for variable fields, to the nodes that want facts matching it.
- **Tokens.** A token (`Wongi.Engine.Token`) is a partial match: its parent tokens, the fact it added (if any), and the variables that fact bound. A parent creates a token *for* a child node (`Token.new(child, ...)`), so `Rete.tokens(rete, node)` holds a node's *input* tokens. Tokens never change after they are created, and a token's `ref` identifies it.

`Wongi.Engine.Compiler` turns each clause of a rule into one or more nodes:

| Clause | Node |
|---|---|
| (start of every rule) | `Root` |
| `has` | `Join` |
| `neg` | `Negative` |
| `ncc` | the subchain's nodes, then an `NCC.Partner` at its end and an `NCC` in the main chain |
| `any` | each branch's nodes, joined by an `Or` |
| filters | `Filter` |
| `assign` | `Assign` |
| `aggregate` | `Aggregate` |
| (end of every rule) | `Production`, which runs the rule's actions |

A node that is equivalent to an existing child of the same parent (`Beta.equivalent?/3`) is reused, so rules that start with the same clauses share nodes.

## How a change propagates

### Asserting a fact

`Rete.assert` puts the fact into memory and records where it came from: manually asserted (`manual`), or generated by a production token (`generation_by_wme` and `generation_by_token`). If the fact is new, `activate` delivers it to each node subscribed to a matching template, one at a time.

- A `Join` receiving a fact (`alpha_activate`) matches it against its input tokens and passes a new token to its children for each match.
- A `Join` receiving a token (`beta_activate`) stores it and matches it against the facts in memory, through a template specialised with the token's values.

The other node types work the same way, through the same two callbacks. A `Production` receiving a token runs its actions straight away. A generator action asserts its facts with the token as their source, which recursively propagates them too, all within the original `assert` call. There is no queue of pending operations; one was tried and removed, because it let aggregates rebuilding their results see stale state.

**A fact must reach a join once.** Facts are delivered to their subscribers in the order of `@alpha_patterns`, not in the order of rules or clauses. So a join can be reached by a fact twice: once through a beta activation, when an earlier subscriber of the same fact produced tokens that reached the join (directly, or through facts generated on the way), and selected the fact from memory; and once more through its own alpha activation. While a fact is being delivered, `pending_alpha` records the subscribers it has yet to reach, and `Join.beta_activate` leaves those facts to the alpha activation.

### Retracting a fact

`Rete.retract` removes one source of the fact. A fact may still have others: it may be asserted manually and generated, or generated by several tokens. But its remaining support may itself depend on the fact, as with facts generated in a cycle (`friend` being symmetric, say), and the fact should then go.

So the fact is removed in any case (delete), along with everything derived from it, and put back and activated again if it is still supported after that (rederive):

1. Delete the fact from memory, and mark it as being retracted (`retracting`).
2. Deactivate it. Every node that holds tokens containing it removes them, and their descendants. A production token that is removed retracts the facts it generated, which may in turn come back to this fact.
3. Unmark it. If it still has a source, put it back and activate it.

The cascade in step 2 can derive the fact again. While it is marked, that only records the new source, and the fact is activated once, in step 3.

### Negations and NCCs

A `Negative` records which facts block which of its input tokens (`neg_join_results`), and passes a token on only while nothing blocks it.

An `ncc` compiles its subchain as a separate branch, starting from the same parent as the `NCC` node, and ending in an `NCC.Partner`. Since both start from the same parent, each partner token has, somewhere in its lineage, a duplicate of the `NCC` input token it was derived alongside, and is owned by that token (`ncc_tokens` and `ncc_owners`). The `NCC` passes a token on only while it owns no partner tokens.

### Compiling a rule

Each new node is seeded by its parents from the current state (`Beta.seed/3`): the parent gives it a token for everything that already matches. Seeding works from a snapshot of the parent's tokens taken before it starts.

A node is subscribed to its parents after it has been seeded, so that it doesn't receive anything twice, with one exception. A `Production` runs its actions as it is seeded, and the facts they generate can produce new tokens in its parent, which it would otherwise never see. So a production is subscribed first, and the tokens it doesn't get from the snapshot arrive through the subscription.

## How tokens are found

Several operations need some of a node's tokens rather than all of them. Two kinds of index answer those questions without scanning. Both are maintained by `Rete.add_token/3` and `Rete.remove_token/3`, and are read but never written by nodes.

### By parent and by fact

For every node:

- `tokens_by_parent` stores a token under each of its parents' refs, read with `Rete.child_tokens/3`. Refs are used rather than the parents themselves to avoid hashing a deeply nested term.
- `tokens_by_wme` stores a token under its own fact, if it has one, read with `Rete.tokens_with_wme/3`.

Removing a token or a fact uses these to find what to remove from the children (`Beta.Common.beta_deactivate/3`).

### By node-specific keys

`node_index` stores each token under keys that its node chooses, through the `Beta.index_keys/2` callback, and is read with `Rete.get_node_index/3`. An empty list of keys means the token isn't indexed.

| Node | Keys | Used for |
|---|---|---|
| `Join`, `Negative` | the values of the variables the node tests facts against | finding the tokens a new fact can match (`JoinKey.candidates/3`) |
| `NCC` | the token's signature | a partner finding the token that owns its new token |
| `NCC.Partner` | the signature of every token in the token's lineage | the `NCC` finding the partner tokens a new token owns |
| others | none | |

**Join and negation keys** (`Beta.JoinKey`). A clause like `has(var(:p), :parent, var(:c))`, after `:p` is bound, tests that a fact's subject equals the token's `:p`. A token's key is the values of the tested variables, in subject, predicate, object order; a fact's key is the values of the same fields. A fact can only match the tokens under its own key, by the same exact equality that `Join.match/3` uses. A variable that the clause itself introduces, like the second `x` in `has(var(:x), :likes, var(:x))`, isn't in the token and is left out of the key. A node with nothing left to key on, typically the first clause of a rule, indexes nothing, and looks at all of its tokens.

**NCC signatures.** A partner token is owned by an `NCC` token when it, or one of its ancestors, duplicates the `NCC` token: same fact, same bindings, same parents. That is the token's signature (`Token.signature/1`). Indexing `NCC` tokens by their own signature and partner tokens by every signature in their lineage pairs them up. Both sides still check the candidates with `NCC.Partner.owner_token?/2`.

## Invariants

1. **Results don't depend on the path taken.** The facts in memory and the matches of every rule depend only on which facts are asserted. They don't depend on the order of the facts, the order of the rules, or whether a rule was compiled before or after its facts. The one exception is the bindings visible after an aggregate (see "Known limitations"). The consistency properties check this (see "Testing").
2. **Retracting everything restores the initial engine,** down to the indexes. Anything else means something was left behind.
3. **Tokens are added and removed only through `Rete.add_token/3` and `Rete.remove_token/3`, by their own node.** Otherwise the indexes are out of date, or the wrong node's keys are used.
4. **`index_keys` depends only on the node and the token.** It is called again on removal rather than remembered, so the keys must come out the same.
5. **An index may return too much, never too little.** Every lookup is followed by the full check (`match/3`, `owner_token?/2`). A node may leave a token out of its index only if the token can't match anything, like a token that doesn't bind a variable the node tests.

## Known limitations

- **Bindings after an aggregate.** An aggregated token has every token of its group as parents, which may bind the same variable to different values. Which one is visible downstream depends on the iteration order of its parents.
- **Aggregates scan.** On every change, a partitioned aggregate regroups all of its tokens, and finds the tokens it produced earlier by scanning its children.
- **Seeding scans.** Compiling a rule visits every token of the nodes it extends, which is inherent.

## Testing

- `test/wongi/engine` has unit tests by node type and DSL feature. `generate_test.exs` has most of the propagation corner cases above, each with a minimal reproduction.
- `test/wongi/scenarios` has four realistic rule sets of 12 to 19 rules each (defined in `test/support/scenarios`), with worked examples for each. `consistency_test.exs` checks invariants 1 and 2 on all of them, with random sequences of assertions and retractions drawn from each scenario's own domain (`Wongi.Scenario` and `fact/0`).

The properties run 100 times each by default, and 1000 times in CI. For a longer run:

```sh
PROPERTY_RUNS=10000 mix test test/wongi/scenarios/consistency_test.exs
```

A failure prints the operations (shrunk by `StreamData`) and the seed used to shuffle the engine built from scratch. Shrinking rarely gets down to a handful of operations, so it usually pays to minimise further by hand: drop operations and rules one at a time while the failure persists. What usually remains is a handful of facts and two or three rules, which makes a good regression test for `generate_test.exs`.

To add a scenario, implement the `Wongi.Scenario` behaviour, add the module to `@scenarios` in `consistency_test.exs`, and check that the fact generator makes every rule fire in a fair share of runs. With uniform random facts, most rules never match anything.

## Benchmarking

`bench/workload.exs` asserts and retracts n people through a join, a negation and an NCC, and times each phase:

```sh
MIX_ENV=prod mix run bench/workload.exs 2000 --runs 5
MIX_ENV=prod mix run bench/workload.exs 2000 --profile retract
```

CI runs it on every build. Results from `main` are kept in the `gh-pages` branch, with a chart under `dev/bench/`. Other builds fail if a phase is more than 1.5 times slower than the latest result from `main`.
